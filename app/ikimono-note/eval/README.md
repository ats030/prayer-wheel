# 識別精度の評価

アプリの表示は「あてはまり度 60%」「決め手なし」など確信度を細かく出すが、その数字が
実態と合っているかは測らないと分からない。安全カードに「まちがえることがあります」と
書く以上、どのくらい間違えるのかは運営者が把握しておく。

## 写真の大きさ

既定で取るのは iNaturalist の `medium`、長辺500pxである。アプリが外部AIへ送る前に
縮める上限は長辺1600px (`vision.MAX_EDGE`) なので、**この既定で測るかぎり上限には
一度も届かない**。`eval/results/` にある成績はすべて、本番より小さい写真でのものだと
思って読むこと。

解像度が効くかどうかを測るときは、写真を取り直してから振る。

```bash
IKIMONO_EVAL_PHOTO_SIZE=original uv run python eval/fetch_dataset.py   # 元の大きさで取る
IKIMONO_MAX_EDGE=1600 uv run python eval/run_eval.py --provider local  # 送る側の上限を振る
IKIMONO_MAX_EDGE=2400 uv run python eval/run_eval.py --provider local
```

上げれば細部は残るが、モデルによってはタイル数が増えて課金と待ち時間が伸びる
(Gemini は768pxのタイルに割り、最大3072pxまで受ける)。

### 測った結果 (2026-08-13、gemma4:31b、同じ100枚)

```
uv run python eval/compare_runs.py edge-1600 edge-2048
```

| 指標 | 1600px | 2048px | →2048で正解 | →1600で正解 | p値 |
|---|---|---|---|---|---|
| Top-1 | 11枚 | 12枚 | 4 | 3 | 1.000 |
| Top-3 | 13枚 | 13枚 | 3 | 3 | 1.000 |
| 属まで一致 | 25枚 | 25枚 | 3 | 3 | 1.000 |
| 科以上 | 78枚 | 74枚 | 7 | 11 | 0.481 |
| 候補ゼロ | 22枚 | 26枚 | 11 | 7 | 0.481 |

**動かなかった。** 1枚あたりの時間も 42.4秒で同じ。よって既定は 1600px のまま。
iNaturalist の original はどれも長辺2048pxなので、この写真では 2048 より上は試せない。

ただし、この結果は「差が無い」ではなく「この測り方では差が見えない」と読むべきである。
**第一候補そのものは100枚中50枚で入れ替わっていた** (コハクチョウ・シマヘビ・
ホシホウジャクなど)。入力の違いは長辺だけで temperature も 0.1 なのに半分が変わる。
雑音がこれだけ大きいと、100枚1回では10ポイント未満の差は検出できない。

### 切り分け: 同じ設定で2回 (2026-08-13、ats030-0rte)

```
uv run python eval/compare_runs.py edge-1600 edge-1600b
```

| 指標 | 1回目 | 2回目 | p値 |
|---|---|---|---|
| Top-1 | 11枚 | 9枚 | 0.500 |
| Top-3 | 13枚 | 11枚 | 0.500 |
| 属まで一致 | 25枚 | 22枚 | 0.375 |
| 科以上 | 78枚 | **65枚** | **0.007** |
| 候補ゼロ | 22枚 | 28枚 | 0.263 |

**第一候補が変わった枚数: 36 / 100。**

設定は完全に同一である。それでも「科以上」が13ポイント動き、有意になった。
**同じ条件どうしで有意差が出るということは、この検定が拾っているのは設定の差ではなく
実行ごとのばらつきである。** 解像度の比較で見た50枚の入れ替わりも、その大半は
解像度ではなく非決定性だった (同一設定でも36枚動く)。

したがって:

- `eval/results` にある成績はすべて1回きりの値であり、10ポイント程度の差では
  何も言えない。過去の数字を「改善した/悪化した」と読まないこと
- 1回100枚の比較で判断してよいのは、この幅を明らかに超える差だけ
- 評価のやり方自体を直す必要がある (複数回まわして平均と幅を出す、種を固定する)。
  gemma4:31b は temperature 0.1 でも決定的ではない

## 検証はOllamaで行う

既定は `--provider local`。外部APIは無料枠に**モデルごとの日次上限**があり、評価を1回
回すだけで公開版の利用者ぶんの枠を削ってしまう。実際、gemini-3.6-flash で30枚を流した
ところ10枚で日次上限に達した (`GenerateRequestsPerDayPerProjectPerModel-FreeTier`)。

外部プロバイダーとの比較が必要なときだけ `--provider gemini` のように明示する。その場合も
中断した続きから再開できる (成功ぶんは結果ファイルから引き継ぐ)。

## データセット

iNaturalist の research-grade 観察から、**CC0 の写真だけ**を集めた30枚。日本 (place_id
6737) に絞り、植物・昆虫・鳥・菌類・は虫類/両生類を6枚ずつ。1種1枚。

ライセンス判断は `~/ai-workflow/tool-license-registry.yaml` に記録済み (conditional)。
条件は CC0 に限ること。`fetch_dataset.py` は `photo_license=cc0` で絞ったうえで、
レスポンスの `license_code` を1枚ずつ再検証し、CC0 以外は保存しない。

画像は再取得できるので `~/cache/species-eval/images` に置き、リポジトリには
`dataset.json` (observation_id と正解ラベル) だけを残す。

```bash
uv run --with httpx python eval/fetch_dataset.py --per-group 6
```

正解ラベルは research-grade 観察の taxon。**これも人間のコミュニティ同定であって絶対では
ない**ので、数%のラベル誤りが混じる前提で読む。

## 測定

```bash
uv run --with httpx --with pillow python eval/run_eval.py --label local-baseline
uv run --with httpx --with pillow python eval/run_eval.py --use-plantnet --label local-plantnet
```

本番と同じ `pipeline.identify_all` を通す。評価だけ別の手順を組むと、測った数字が
アプリの実際の挙動と静かにずれるため。

| 指標 | 意味 |
|---|---|
| top1 / top3 | 第1候補 / 上位3候補に正解の学名が入るか |
| genus | 上位3候補のいずれかが正解と同じ属か |
| family_or_above | 属が外れていても、上位分類が正解の系統と重なるか |
| rejected | 候補を1件も出さなかった割合 |
| mean_confidence_when_answered | 答えたときの平均確信度。top1 と大きく離れていれば校正がずれている |

結果は `results/<label>.json`。要約と1枚ごとの内訳が入る。

## 読み方の注意

- 30枚は傾向を見るには足りるが、数ポイントの差を断定できる量ではない。
- 分類群ごとに難易度が違う。全体の数字だけでなく `rows` の group 別を見る。
- `rejected` が高いのは必ずしも悪くない。誤断定を避けた結果なら設計どおり。
  `top1_percent_when_answered` と併せて見る。

## 測定結果

### Pl@ntNet 併用の効果 (植物20枚・Ollama・同一写真)

| | Top-1 | Top-3 | 属 | 科以上 | 棄却 |
|---|---|---|---|---|---|
| ローカル単独 | 0% | 0% | 0% | 85% | 15% |
| Pl@ntNet 併用 | **45%** | 50% | **65%** | **100%** | 0% |

専門識別は20件すべてで実行された。Top-1 が入れ替わったのは9枚で、**すべて併用側が正解**。
併用にして外した写真は1枚もなかった。

結論: Pl@ntNet 経路は残す (ats030-xzxs)。Ollama単独では植物の種同定がほぼ
成立せず (属レベルでも 0%)、専門識別が精度の大半を担っている。

### 分類群ごと (Ollama単独・30枚)

| 分類群 | Top-1 | 科以上 | 棄却 |
|---|---|---|---|
| 鳥 | 33% | 67% | 33% |
| 菌類 | 17% | 67% | 33% |
| は虫類・両生類 | 17% | 83% | 17% |
| 植物 | 0% | 83% | 17% |
| 昆虫 | 0% | 67% | 33% |

### プロバイダー比較 (同一10枚)

| | Top-1 | 属 | 科以上 | 中央値 |
|---|---|---|---|---|
| ローカル (gemma4:31b) | 10% | 20% | 90% | 61.5s |
| Gemini 3.6 Flash | 30% | 40% | 90% | 18.1s |

Gemini 側は無料枠の日次上限で10枚までしか回せていない。傾向以上の主張はできない。

## Gemini の無料枠はモデルごとに違う

`gemini-3.6-flash` は1日20リクエストしか通らない (2026-08-11 実測、429 の
`GenerateRequestsPerDayPerProjectPerModel-FreeTier` に `quotaValue: 20`)。30枚の
評価が完走できず、公開版の既定にはできない。`gemini-3.5-flash-lite` は30枚を
完走している (Top-1 36.7%)。

同じ10枚で比べたときの精度に差は出ていないため、無料枠の広さで Flash-Lite を
既定にした。枠は予告なく変わるので、既定を変える前にこの数字を測り直すこと。

## thinkingLevel は high のまま

同じ日・同じコードで gemini-3.5-flash-lite を30枚ずつ測った (2026-08-11)。

| thinkingLevel | Top-1 | Top-3 | 属 | 科以上 | 中央値 | 棄権 |
|---|---|---|---|---|---|---|
| high | 40.0% | 40.0% | 53.3% | 96.7% | 10.5秒 | 3.3% |
| medium | 26.7% | 33.3% | 50.0% | 90.0% | 6.8秒 | 10.0% |

medium は3.7秒速いが、Top-1 が13.3ポイント落ち、棄権が3倍に増える。全ての指標で
high が上回っているので high を既定に据え置く。ただし30枚での13.3ポイントは4件差
であり、偶然の幅を完全には否定できない。据え置きの判断としては足りるが、逆の
結論 (medium へ下げる) を出すには枚数が要る。

thinkingLevel を記録していなかったため、これ以前の gemini 結果がどちらの条件
だったか確かめられない。run_eval は config.thinking_level を残すようにした。

## 30枚では施策の良し悪しを判定できない (2026-08-11)

Pl@ntNet の有無を比べたとき、Pl@ntNet が触らないはずの分類群で 24件中4件 (17%) が
入れ替わった。

| | 変化 |
|---|---|
| 昆虫 イボタガ | ○→× |
| 鳥 エナガ | ○→× |
| 菌類 シロソウメンタケ | ×→○ |
| は虫類 シマヘビ | ○→× |

VLM は同じ入力でも同じ答えを返さない。分類群あたり6枚では1件が 17ポイントを動かし、
施策による差がこのばらつきに埋もれる。全体 Top-1 の差 (40.0% → 33.3%) も30枚中2件の
差でしかなく、Pl@ntNet が効いたのか偶然かを分けられない。

**これ以前に出した数字はすべて、分類群あたり6枚で測っている。** 「Flash-Lite と
Flash 3.6 に精度差がない」「thinkingLevel high が medium より13.3ポイント良い」と
いった結論も、差 (4件) がばらつき (4件) と同じ大きさで、判定に足りていなかった。

分類群あたり20枚 (計100枚) に増やした。1件の変化が5ポイントに収まる。それでも
小さい差は判定できないので、10ポイント未満の差は「分からない」として扱うこと。

## Pl@ntNet は残す。BioCLIP は見送る (2026-08-12)

100枚で測り直した。1件が1ポイントなので、30枚の頃より細かく見える。

| 条件 | Top-1 | 属 | 科以上 | 棄権 |
|---|---|---|---|---|
| Gemini Flash-Lite のみ | 31.0% | 48.0% | 87.0% | 13.0% |
| + Pl@ntNet | **40.0%** | **60.0%** | 91.0% | 9.0% |

差は9件。ばらつき (実測で4件程度) を超えており、全指標が同じ方向へ動いている。
30枚で測ったときは「Pl@ntNet ありのほうが悪い (40%→33%)」と出ていたが、枚数不足に
よる誤りだった。

### BioCLIP 2 (MIT) を試した結果

VLM が出した候補を BioCLIP で並べ替える形で測った (eval/bioclip_rerank.py)。

| 元にした結果 | 並べ替えた件数 | 効果 |
|---|---|---|
| v2-base | 64件 | +6件 (+9.4pt) |
| v2-plantnet | 74件 | +2件 (+2.7pt) |

**植物では両方とも効果ゼロ。** 効いたのは は虫類・両生類、菌類、鳥で、Pl@ntNet が
触らない領域だった。ただし2回で +6 と +2 に割れた。並べ替え自体は決定的だが、入力に
なる VLM の候補がばらつくため、効果も run ごとに変わる。平均 +4件はばらつきと同じ
大きさで、100枚では確定できない。

torch (数GB) とモデル (1.7GB) を抱え、Cloud Run の無料枠では動かせない。効果が
確定していないものに、この重さは引き受けられないと判断した。スクリプトは残してある。

### 植物向けのオープンモデルは見つからなかった

- **PlantCLEF 2024** (`vincent-espitalier/dino-v2-reg4-with-plantclef2024-weights`):
  CC BY-NC で商用不可。かつ south-western Europe の 7,806種が対象で、日本の植物に
  合わない
- **BioCLIP 2**: MIT・全球だが、上記のとおり植物では効かなかった
- **GBIF**: 分布データはオープンだが、外している例は「どちらも日本に分布」する
  組み合わせが多く (オオカナダモ↔トチカガミ)、絞り込みでは分けられない

Pl@ntNet はモデルこそ非公開だが、1日500件まで商用でも無料で、代替が存在しない。
オープン中心の方針に対する例外として残す。

## 撮影地域の与え方を変えて測る用意 (2026-08-12)

「日本」では広すぎて効かなかった (Top-1 40.0% で変化なし)。与え方を変えて測れる
ようにしてある。データセットには座標・日時・標高・周辺の土地利用が入っている。

| 渡し方 | オプション | 例 |
|---|---|---|
| 固定の文字列 | `--location 日本` | 日本 |
| 座標 | `--location-from-coordinates` | 緯度 35.2900, 経度 139.5800 |
| 地名 | `--location-from-place` | Shinjuku, Zushi, Kanagawa, Japan |
| 標高と土地利用 | `--location-from-geo` | 日本、標高8m、周辺は農地 |
| 撮影日 | `--date-from-dataset` | 2025-05-29 |
| 撮影日時 | `--time-from-dataset` | 2025-05-29 17:24 |

座標そのものは VLM にとってただの数字で、分布の知識と結びつきにくい。標高と土地利用に
直せば意味のある手がかりになる、という見込みで用意した。効くかどうかは未測定。

アプリは EXIF の撮影日時から日付だけを取り出しており、**時刻を捨てている**
(`str(captured)[:10]`)。夜行性か昼行性かは、ガとチョウのような相手を分ける手がかりに
なる。これも測れるようにした。

### 使ったオープンデータ

- 標高: 国土地理院 標高API (政府標準利用規約。出典の明示が要る) — 96/100件で取得
- 土地利用: OpenStreetMap Overpass API (ODbL。出典の明示が要る) — 70/100件で取得。
  山林などマッピングの疎な場所では何も返らない

アプリに組み込むときは、どちらも出典の明示が要る。

## 撮影の文脈は効かなかった (2026-08-12)

Pl@ntNet ありを基準に、撮影地域と日時の与え方を4通り測った。いずれも Top-1 を
上げていない。

| 与えた情報 | Top-1 | 属 | 科以上 | 棄権 |
|---|---|---|---|---|
| なし | **40.0%** | 60.0% | 91.0% | 9.0% |
| 「日本」 | 40.0% | 61.0% | 93.0% | 7.0% |
| 標高と土地利用 | 36.0% | 59.0% | 88.0% | 12.0% |
| 撮影日時 (時刻まで) | 34.0% | 59.0% | **94.0%** | **6.0%** |

外している中身を見ると理由が分かる。シマヘビ↔アオダイショウ、コハクチョウ↔
オオハクチョウ、イボテングタケ↔テングタケ — **同じ場所・同じ季節にいる近縁種**
ばかりで、文脈をどれだけ精密にしても2択は絞れない。要るのは写真から鱗や嘴を読む力で、
そこは VLM の視覚的な限界に属する。

Pl@ntNet が効くのは、植物の画像を専門に学習したモデルが「見て」判断しているからで、
文脈を足すのとは質が違う。**文脈情報で伸ばす路線は打ち止め**とする。

撮影日時は科以上の正答が最も高く (94.0%)、棄権も最少 (6.0%) だった。大枠の判断には
寄与しているが、種の特定には届いていない。
