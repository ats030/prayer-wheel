# 無料の公開生成：認証・利用制限の設計

設計日: 2026-10-11。設計issue: ats030-1b9h0。これは実装契約であり、現行の私用APIに認証や制限が導入済みという意味ではない。

## Verdict

proceed。設計を確定し、私用データから分離した公開生成の実装へ進める。一般公開はWikipedia品質比較・権限試験・無料プラン確認の完了後とする。

## Decision

既存のローカルAIとFIFOを使い、少人数に無料生成を提供する。初期は招待10人を想定する。Cloudflare Accessでログインし、Tunnelで別ポートの公開用アプリへ接続する。公開用アプリは別SQLite DBを持ち、同じ既存コードのキューを再利用する。私用アプリのDB・HTTPポート・管理操作は接続対象にしない。

初期は公開用アプリが短い受付応答を返し、その後に既存QueueWorkerが生成する。HTTP接続を60分維持しない。Cloudflare側に新しいDBや受付キューを設けない。この構成なら手元サーバー停止中には新規受付できないため、画面に停止中を表示する。

## Strongest objection

Cloudflare Accessの無料枠は50ユーザーまでで、不特定多数向けの会員基盤として拡大し続けられる設計ではない。ローカル生成が1件60分なら全体10件で最大10時間の処理を受け付ける。サーバー故障・電気代・共有モデルの混雑も残る。初期の実利用を測り、招待人数と受付数を増やす前に方式を再検討する。

## Evidence

観測: `server.py` はアプリ内認証を行わず、`JobStore.listing/get` に所有者条件がない。同じテーマは全体で共通のcache_keyになり、APIには編集・中止・再生成・削除がある。Origin/Host検査はDNS rebinding対策で、利用者の本人確認ではない。

観測: FIFO・単一ワーカー・永続保存・60分の強制終了・途中結果の保存・再起動後の再開は既存実装にある。これを再利用する。Cloudflareの料金表はAccess無料枠50ユーザー、公式文書はオリジンでのAccessトークン検証を説明する。

仮定: 初期の需要は少人数で、即時完成より、無料で受付・結果を確認できることを優先する。10人・全体10件/日は容量試算の開始値で、需要の実測値ではない。

判断: 新しいクラウドキューより既存構成を再利用し、所有者保護と原子的な受付制限を先に実装する。ローカル停止中の受付継続は初期要件にしない。

| 選択肢 | 適合・負担・判断 |
|---|---|
| 私用のまま維持 / 公開閲覧だけ | 追加費用と権限リスクは小さいが、利用者による生成という要求を満たさない。私用環境と公開済み静的年表は維持する。 |
| Access・Tunnelと既存キューの再利用 | 初期招待制に適合。正本は公開用SQLite、運用者が管理。所有者検査とクォータを追加し、公開用サービスを止めれば撤回できる。停止中の受付は不可。採用候補。 |

## Guardrails

### 認証と接続

ログインはAccessの招待許可リストで行う。アプリ側も `Cf-Access-Jwt-Assertion` の署名・固定したissuer・アプリ固有audience・exp・nbf（存在する場合）・利用者subjectを検証する。JWT本文をdecodeしただけの値、メールヘッダー、IP、クライアント指定ownerは本人確認に使わない。サービス用トークンを一般利用者として扱わない。

JWKSの取得先は運用設定のteam domainに固定する。トークンのURLを使わない。鍵ローテーションを考慮し、取得にはタイムアウト・有効期限付きキャッシュ・更新頻度の上限を設ける。未知鍵や失敗時には検証済みの有効な鍵を使える場合以外、保護APIを拒否する。issuer/audienceなどの必須設定が欠ければ公開用サービスを起動しない。検証には保守されるJWTライブラリを使い、具体的な依存バージョンの利用条件・脆弱性は実装時に確認する。

Tunnel側もProtect with Accessを有効にし、公開用アプリをloopbackにbindする。GPU・検索・モデル・管理APIはTunnelの経路にしない。静的ページを他のホストで公開する場合も、認証済みAPIへの抜け道を作らない。公開ホストとHTTPS Originを明示し、任意のHostやX-Forwarded-*を信頼しない。状態変更には同一OriginとCSRF対策を適用する。私用HTTPのOrigin条件を一般的に緩めない。

### 所有者とAPI

所有者の正本は検証済み `(issuer, subject)` から作る内部ID。メールやテーマを識別子にせず、所有者をDBに記録する。所有者なしの旧データを利用者へ割り当てない。公開用DBは空から作り、私用履歴を移さない。cache_keyは所有者と正規化テーマを含め、他人の検索履歴や指定項目を再利用しない。

| 現行経路 | 公開版での契約 |
|---|---|
| `/`, `/changelog`, `/timelines`, `/quality`, JS/CSS/icon | パイロットのアプリ画面はAccess配下。公開説明ページは別の静的ページに分離可能。 |
| `GET /api/jobs` | 本人の一覧・本人の総数だけ。offsetも所有者条件内で適用。 |
| `GET /api/jobs/:id`, `/timelines/:id` | 本人だけ。存在しないIDと他人のIDは同じ404。 |
| `GET /api/quality` | 本人の結果だけ。全員の検索テーマ・件数を漏らさない。 |
| `POST /api/jobs` | 本人の保存結果だけ再利用。新しい計算には全上限を適用。 |
| `POST /api/jobs/:id/{retry,regenerate}` | 本人だけ。追加計算として日次枠を消費する。待機/生成中の同じ処理は新たに受付しない。 |
| `POST /api/jobs/:id/{cancel,milestones}` | 本人だけ。編集の版チェックを維持。中止・編集は生成枠を増やさない。 |
| `POST /api/jobs/:id/delete` | 本人のデータだけ。公開版では完了結果も削除可能にする。日次使用量は削除しない。 |
| `GET /api/health` | 運用用。本人認証を要求し、検索条件・内部URL・モデル名を返さない。外部の停止画面は汎用表示。 |

初期の共有・自動公開は無効。第三者向けの公開は運用者が確認した静的書き出しを別に使う。詳細APIの応答は許可フィールドを列挙し、quote、trace、内部ID、JWT、メール、内部エラーを返さない。POSTの受付・再生成応答にも同じ制限を掛ける。

公開用サービスは起動時に `TIMELINE_SOURCE=wikipedia` を必須とし、未設定・別値なら起動を拒否する。私用サービスの既定値を継承しない。起動検査と生成結果の `source_mode` を回帰試験で確認する。

### 受付制限

| 制限 | 初期値 | 対象 |
|---|---:|---|
| 利用者の新しい生成 | 1件/日 | 新規・再生成・再試行を合算。日本時間0時に日付が変わる。 |
| 全体の新しい生成 | 10件/日 | 日付をまたぐ実行は受け付けた日の枠を使う。 |
| 利用者の未完了処理 | 1件 | queued + running。日付変更で枠が戻っても未完了があれば追加受付不可。 |
| 全体の未完了処理 | 3件 | queued + running。最大2件待機＋1件実行。 |
| 同時生成 | 1件 | パイロット期間は私用ワーカー・品質測定とも重ねず、公開開始前に停止・時間帯調整する。 |
| 1件の処理時間 | 60分 | 既存の強制終了・検証済み途中結果保存を維持。 |

受付・クォータ記録・キュー投入を同じSQLiteの `BEGIN IMMEDIATE` トランザクションで行う。上限の確認と挿入を別トランザクションにしない。generation_admissionsには所有者、受付ID、受付時刻、日付を保存し、ジョブ削除と連動削除しない。日次集計はこの台帳から行い、メモリや一覧件数で判定しない。DBエラー時は受付しない。

拒否時はHTTP429と機械判定可能な理由（user_daily/global_daily/user_pending/global_pending）を返す。日次超過は次の日本時間0時までのRetry-After、混雑は暫定60秒を返す。画面の再送は自動でループさせない。レスポンス喪失後の再送は、台帳の一意キー（所有者・受付ID）をクォータ判定より先に照合する。操作、対象ジョブ、正規化した入力の指紋を保存し、同じIDを別操作・対象・入力へ使う場合はHTTP409で拒否する。同一入力の再送は元の受付を返し、追加枠を消費しない。削除済みの場合は台帳の削除印からHTTP410を返し、再生成しない。受付IDの再送保証期間は台帳保持期間の90日とし、古いIDを新規受付に再利用しないよう受付IDの発行期限も検証する。

処理失敗・中止・結果削除でも消費した枠は戻さない。運用側障害を補償する場合は、運用者が理由付きで別の補償記録を作り、履歴を消さない。再起動後の同じ受付の再開は追加課金・追加枠を伴わない。同一利用者の保存結果の閲覧・再利用は枠を使わない。全体3件の上限により最悪待機は概算で最大2時間、生成は別に最大1時間かかる。実際の待機時間は処理時間の実測から幅で示し、完成時刻を断定しない。

### 費用・保持・運用

Cloudflareの有料プラン、Workers AI、有料検索APIは初期採用しない。Access無料枠を超える招待を止め、無料枠や規約変更で継続できなければ受付を停止して再検討する。電気代・機器・回線・ドメイン費は残る。日次件数だけで電気代の上限は保証しない。既存モデルの検証fallbackや混雑も処理時間に影響する。

公開用結果と指定項目は最終更新から30日保持し、期限を画面に示す。削除・期限切れで本人の結果を削除し、クォータ台帳は90日保持する。台帳は検索本文を持たない。進行中の処理は期限削除せず、終了後に整理する。バックアップも同じ保持方針を適用し、30日保持の結果を永久に残さない。30日経過の結果を他人に再利用させない。生成枠を消費する定期自動再生成はしない。

監視は受付数、拒否理由、queued/running数、処理時間、失敗・途中終了、DB容量を集計する。ログに検索本文・指定項目・JWT・メール・原文引用を出さない。公開用DB容量が128MiB以上になったら新規計算を止める。容量上限だけでは実行中の増分やバックアップまで保証できないため、ディスク空きも監視する。日次10件・30日で最大300結果、各50出来事なら最大15,000出来事が目安。

所有者漏えい、上限超過、無料枠を超える設定を検出したら、公開受付を停止しTunnelの当該経路を無効にする。私用サービスは別DB・別ポートで維持する。ロールバックは公開用サービスの停止とコードの切り戻しで行い、私用DBを上書きしない。公開用の台帳・所有者スキーマを旧版へ雑に戻さず、読取専用で退避する。

書籍広告はログイン限定画面へAPIデータを配る前提にしない。条件を確認した手動リンクを、公開の確認済み年表または説明ページにPR表示付きで置く。年表本文の帰属条件と広告素材の条件は [PUBLIC_LICENSE.md](PUBLIC_LICENSE.md) に従う。

## Smallest next step

公開用の別DBで所有者条件と原子的な受付制限を実装し、実モデルを呼ばず、2利用者・並行HTTPリクエスト・再起動で検証する。その後Access JWT検証と公開ホストのOrigin条件を統合する。DNS、Tunnel、Accessの実設定は、ローカル検証を終えた具体的な構成で行う。

Cloudflareのteam domain、Application AUD、公開ホスト、許可利用者、実際の無料プラン状態は未確認。値がない状態で仮の認証を通したり、公開URLを作ったことにしない。接続設定に必要な情報は実装・検証を済ませてから具体的に確認する。

## Success and stop criteria

| 試験 | 合格条件 |
|---|---|
| 認証 | 未署名、改変、期限切れ、別issuer/aud、サービス用トークン、未知鍵、設定欠落を拒否。有効な利用者だけ受付でき、鍵ローテーション時も検証を維持。 |
| 所有者 | 2利用者の全GET/POSTを交差試験し、他人の本文・テーマ・指定項目・一覧総数を返さない。管理者向けの迂回経路が一般利用者から呼べない。 |
| クォータ | 境界値、20並行受付、UTC/JST日付境界、上限到達後の同一受付再送、異なる入力でのID再使用、削除後の再送、削除、中止、失敗、再起動で上限を超えない。受付/台帳/キューの途中失敗が全てrollbackする。 |
| 資源 | 既存の60分停止試験を継承し、全ワーカーの同時実行1を確認。検索・AI・私用APIへの直接経路がない。DB容量停止と保持期限を検証。 |
| UI | 使用済み枠・次の受付日・待機数・停止中・認証期限切れを表示。320〜1280px・200%・キーボードで検証。本人にだけCC表示付きの結果を返す。 |
| 公開 | Wikipedia6テーマ比較と出典監査、アカウント/無料プラン、HTTPS・Origin・実JWT・バックアップ・復旧試験を完了。旧結果の自動公開はしない。 |

品質比較が未完了の間もローカルの権限・制限試験は進められる。品質不足で一般公開できない場合は測定と修正を継続し、権限実装の成功を年表品質の合格と混同しない。
