# 歴史年表

キーワードから歴史の全体像を読む、個人用Webアプリです。
一つの入力欄で複数のキーワードと年代条件を指定し、Webの本文に根拠がある出来事を日本語の年表に整理します。
主要な出来事10〜15件を目標にしますが、出典照合で残った分だけ表示します。

## 起動

Python 3.10以降の標準ライブラリ（sqlite3を含む）だけで動作します。新たなPython/JS依存パッケージや有料APIは不要です。

```sh
python3 app/timeline-generator/server.py
```

既定では `http://127.0.0.1:8532/` で起動します。
同梱のsystemdユニットはこのホストのTailnet IP `100.94.207.13:8532` に限定してbindします。
アプリ内ログインはありません。一般公開用の設定ではなく、同じTailnetで許可された端末から利用する個人用初期版です。

環境変数:

|変数|既定値|用途|
|---|---|---|
|`TIMELINE_HOST`|`127.0.0.1`|待受アドレス|
|`TIMELINE_PORT`|`8532`|待受ポート|
|`TIMELINE_SEARCH_URL`|`http://127.0.0.1:8081`|既存SearXNGのJSON検索|
|`TIMELINE_OLLAMA_URL`|`http://127.0.0.1:11434`|既存Ollama互換プロキシ|
|`TIMELINE_MODEL`|`gemma4:12b`|年表候補を生成する既存のローカルモデル|
|`TIMELINE_VERIFY_MODEL`|`qwen3.8:27b`|資料と候補を照合する既存のローカルモデル|
|`TIMELINE_DB`|アプリ内 `data/timelines.sqlite3`|キューと生成結果の保存先|

接続先は運用者が設定する信頼された内部サービスです。利用者が接続先を変更するAPIはありません。
既存の `8527` はこのホストでは別アプリが使っていたため、検索APIとしては利用しません。

## 入力例

- `コーヒー`
- `半導体 日本 1980年以降`
- `京都 1900〜2000年`
- `ジャズ 20世紀`
- `ローマ 紀元前500年〜100年`

年代条件は数字の西暦・紀元前を使います。`以前`、`まで`、`以降`、`から`、数値の範囲、数値の世紀を扱います。
`1980年代`、和暦や複雑な自然文の年代指定はエラーにし、対応形式を案内します。
年代指定がなければ全期間が対象です。曖昧なテーマでは、追加キーワードで絞り込んでください。

## キューと保存した年表

入力欄から一件ずつキューに追加します。登録順に一件ずつ生成し、生成中も次のテーマを追加できます。
画面を閉じても処理は続きます。サーバー再起動時は、中断された一件を最初から生成し直し、その後に待機分を処理します。
生成が失敗しても次のテーマへ進みます。自動で失敗を繰り返さず、個別ページの「再試行」でキューの末尾へ戻します。

`/timelines` は待機中・生成中・完了・失敗の一覧です。新しい登録順に50件ずつ表示し、定期的に更新します。
`/timelines/<id>` は個別ページです。進捗、生成日時、保存した年表、出典、引用を確認できます。

キーワードはNFKCで全角・半角をそろえ、テーマの余分な空白をまとめ、解析した開始年・終了年と組み合わせて比較します。
「半導体 日本 １９８０年以降」と「半導体　日本 1980年から」は同じ扱いです。語順、別名、大文字・小文字、期間が違えば別扱いです。
同じテーマ・期間では期限なしで保存結果を再利用します。待機中・生成中の再登録では重複した処理を作りません。
保存結果がない失敗済みの再登録では、個別ページから再試行できます。

最新情報が必要な場合は「再生成」でキューの末尾に追加します。再生成中・失敗時も前回の年表を閲覧でき、成功した時だけ結果を置き換えます。
今回は一括登録、削除、キャンセル、一般公開は追加しません。

APIは `POST /api/jobs`（`{"query":"京都"}`）、`GET /api/jobs?offset=0`、`GET /api/jobs/<id>`、
`POST /api/jobs/<id>/retry` と `/regenerate`（空のJSONオブジェクト）です。旧ストリーミングAPI `/api/timeline` は置き換えました。
登録は保存完了後に返答し、生成の完了を待ちません。更新APIには従来のHost/Origin検査を適用します。

## 更新履歴

利用者向けの更新履歴は `/changelog` で閲覧できます。
機能追加・使い方の変更・不具合修正を行ったときは、`changelog.html` に日本時間の日付と短い説明を追記します。
日付の新しい順に並べ、同日の変更は同じ日付の項目にまとめます。実装済みの変更だけを掲載します。
画面の見え方や動作に影響しない内部の整理は掲載しません。

## 根拠の扱い

1. 日本語と英語の歴史関連クエリで既存のWeb検索を使います。
2. 最大10ページを取得し、歴史の資料になる箇所がある最大5ページを使います。年代見出しを保持し、ページの初期・中間・末尾と転換点から抜粋します。検索スニペットは史実の根拠にしません。
3. LLMが日本語の出来事と、対応する短い原文引用を提案します。
4. 引用が取得本文に実在すること、年代の数値、紀元前の符号、出典ID、入力した年代範囲、説明の英数字固有名詞を機械で検査します。取得本文と出典タイトルにない英数字固有名詞は、誤記や推測を防ぐため除外します。この保守的な検査では英語名の別表記も除外されることがあります。
5. 年代見出しと候補の年の一致、伝承の留保を検査します。別のローカルモデルの呼び出しで、引用の段落・周辺文脈・比較資料が日付と説明を裏付けるか、入力テーマから逸脱していないか照合します。照合処理が失敗した場合は年表を公開せずエラーにします。
6. 残った出来事を年代順に表示します。世紀しか分からない出来事は、正確な年を推測せず世紀で表示します。

起源・最初の出来事は、残り時間に余裕がある場合に一度だけ追加検索します。最大6ページを追加取得し、最大3ページの比較資料を照合に使います。追加取得の予算は20秒で、照合時間を確保できない場合は省略します。矛盾や伝説を理由に見送った候補には理由と比較資料へのリンクを表示します。モデルの呼び出しは生成と照合の計2回です。

引用は画面の「根拠を見る」で確認でき、出典のタイトル・本文の見出し・原文URLを添えます。資料で月日まで確認できた出来事は月日を表示します。
検索順位や出典リンクは史実の真偽の保証ではありません。異なるモデルでの照合も、独立した人間のファクトチェックではありません。
原資料の誤り、資料間の矛盾、モデルの誤訳や見落としは残り得ます。矛盾や伝説を断定しないよう指示していますが、網羅的な矛盾検出は初期版の保証範囲外です。

robots.txtを尊重し、本文の取得に失敗したページは使いません。HTTP/HTTPSの公開IPのみを接続対象にし、接続するIPを固定します。リダイレクト先も再検査します。
ページ内の指示は資料データとして扱います。取得上限、生成上限、同時生成1件で負荷を抑えます。
1〜2分は目標です。混雑や取得失敗で長くなることがあり、処理全体の時間予算は180秒、待機キューの時間は180秒に含めません。
検索処理はキューの一件ごとに使い捨てプロセスで実行し、DNSや遅い応答本文で処理が止まっても、サーバー側の絶対時間上限で終了させます。

## 保存と費用

入力、処理状態、検証済みの年表、出典URL・タイトル、短い引用、生成日時をSQLiteに保存します。保存期限はありません。取得ページ全文は保存しません。HTTP応答は `no-store` です。
保存先はGit管理対象外です。既定の新規データディレクトリは所有者のみアクセス可能、DBとロックファイルは0600です。Tailnetの許可された端末から保存結果を閲覧できるため、個人用のアクセス設定を維持してください。
検索サービスの上流には検索語が送られます。既存検索・LLMプロキシの運用ログやvisit-logはそれぞれの保存方針に従います。
このアプリのHTTPログには検索語や応答本文を出しません。

新しいAPI料金やソフトウェア利用料は導入しません。既存サーバーの電力・通信・運用費は残ります。
ソフトウェアの利用許諾は取得先の本文の再利用許諾とは別です。利用条件は `tool-license.yaml` に記録しています。
一般公開・収益化は、取得先の利用条件、引用/翻案、利用者認証、レート制限、費用を別途確認してから進めます。

## 検証と復旧

```sh
python3 -m unittest discover -s app/timeline-generator -v
node --check app/timeline-generator/app.js
python3 app/timeline-generator/smoke.py コーヒー
python3 app/timeline-generator/smoke.py インターネット 1980年以降
```

`smoke.py` は実際の検索・本文・モデルを使い、結果と時間を標準出力に出します。保存したサンプルで成功を装いません。
ブラウザ検証は `browser_check.py` で、画面幅・操作・処理中・空結果・エラー・引用表示を確認します。
既存の開発用Playwright/Chromiumを使います。`--live インターネット 1980年以降` を追加すると、UIテスト後に実検索も検証します。
停止は `systemctl --user stop timeline-generator.service`、無効化は `systemctl --user disable timeline-generator.service` です。
DBを安全にバックアップするにはサービスを停止してから、`data/` をコピーしてください。停止中のDBは `PRAGMA integrity_check` で検査できます。
DBを削除すると入力・待機分・結果が失われます。復旧はサービス停止→バックアップを戻す→起動の順です。
同じDBを使う二重起動はファイルロックで拒否します。ワーカーで保存不能になるとプロセスを異常終了させ、systemdの再起動に委ねます。ディスク容量や権限の問題は修正が必要です。
ロールバックはサービス停止→この変更前のコードへ戻す→起動です。保存ディレクトリは残し、旧コードは参照しません。


## 品質改善と保存結果の更新

生成パイプラインの改修は保存済み結果に自動適用しません。同じキーワードは保存済み結果を返し、詳細ページの「再生成」で更新します。再生成はキューの末尾に入り、成功するまで前回結果を保持します。取得や照合に失敗した場合も前回結果を閲覧できます。

2026-10-02の品質改善では、旧4件をSQLiteオンラインバックアップ `data/quality-before-3fxm4.sqlite3` に退避してから更新します。バックアップはローカル限定・Git対象外・権限600です。コードの切り戻しは品質改善コミットをrevertしてサービスを再起動します。結果の切り戻しはサービスを停止し、退避DBの対象IDの結果と生成日時だけを戻します。後から追加された別のジョブを消さないよう、DB全体を上書きしません。

見出しの年代、段落の文脈、伝承の留保、期間・原文一致を機械検査し、別モデルでも照合します。ただし出典自体の誤りや重要項目の見落としは残ります。件数や引用一致を史実の正答率とみなさないでください。
